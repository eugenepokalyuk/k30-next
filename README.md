# k30-next

Витрина магазина подписок «К30» (k30market.ru): покупатель вводит ключ,
сайт определяет сервис и доводит его до активации.

Бэкенд живёт отдельным проектом — [k30-api](../k30-api). Без него витрина
поднимется, но список сервисов и активация работать не будут.

| Что        | Чем                                          |
| ---------- | -------------------------------------------- |
| Фреймворк  | Next.js 16, App Router                        |
| UI         | React 19, SCSS Modules                        |
| Данные     | Redux Toolkit + RTK Query                     |
| Анимации   | framer-motion                                 |

Раскладка папок взята с `divodivnoe`, конфиги eslint / prettier /
stylelint — с `face`.

## Запуск

```bash
npm install
cp .env.example .env.local
npm run dev                   # localhost:3000
```

Бэкенд при этом должен быть поднят на `localhost:8000` — см. README
k30-api.

### Переменные окружения

| Переменная                     | Зачем                                    |
| ------------------------------ | ---------------------------------------- |
| `NEXT_PUBLIC_API_URL`          | Адрес бэкенда. Публичная: запросы уходят из браузера |
| `NEXT_PUBLIC_APP_URL`          | Канонический адрес витрины — для метаданных |
| `NEXT_PUBLIC_SUPPORT_TELEGRAM` | Телеграм поддержки в шапке и подвале      |
| `NEXT_PUBLIC_BASE_PATH`        | Подкаталог сайта. Нужен только на Pages без своего домена |

## Страницы

| Маршрут     | Что там                                                          |
| ----------- | ---------------------------------------------------------------- |
| `/`         | Герой с полем ввода ключа, лента сервисов, «как это работает», вопросы |
| `/activate` | Активация: четыре шага от кода до выданной подписки              |
| `/login`    | Вход                                                             |
| `/register` | Регистрация                                                      |
| `/account`  | Профиль, заказы и история активаций                             |

Проверив ключ на главной, результат кладём в стор и переходим на
`/activate?key=…` — второго запроса за инструкцией и полями не нужно.
Страница всё равно умеет запросить их сама: по прямой ссылке или после F5
стора нет, и это нормальный путь, а не ошибка.

## Активация

Четыре шага: **Ключ → Аккаунт → Активация → Готово**.

Проверка данных и подтверждение разделены намеренно. Между ними
покупатель видит, **на какой именно аккаунт** уедет подписка, — а
перепутанный аккаунт это ровно та ошибка, которую после активации уже не
отменить.

Три вещи, которые определяют устройство этой страницы:

**Состав формы приходит с бэкенда.** Витрина не знает, у какого
поставщика куплен ключ, и не должна: один и тот же сервис у разных
поставщиков просит разные данные (Organization ID против User ID).
Поле `targets` в ответе `verify-key` описывает, что показать; когда
вариантов несколько, даём выбрать. Захардкодить это здесь нельзя.

**Активация асинхронная.** У Claude она занимает около двух минут, и
экран ожидания (`ProgressStep`) — не украшение: без него запрос просто
«висел», а покупатель, не понимая, идёт что-то или нет, жал кнопку
повторно. Показываем позицию в очереди и счётчик времени; через две
минуты честно говорим, что ждать у экрана необязательно — вкладку можно
закрыть и вернуться по той же ссылке.

Темп опроса диктует бэкенд полем `poll_after`: у поставщиков разные
лимиты, и знание о них живёт на той стороне. Хук — `lib/hooks/
useActivationPolling.ts`.

**Тон ошибки выбирается по `blame`, а не по тексту.** «Вы вставили данные
не из того аккаунта» (`customer`), «у поставщика кончились подписки»
(`provider`) и «это на нашей стороне» (`shop`) требуют от покупателя
совершенно разного, а выглядели бы одинаковым красным прямоугольником.
Кнопку «Повторить» показываем только когда бэкенд разрешил
(`can_retry`) — у части поставщиков карта после неудачи заморожена, и
вторая попытка либо бесполезна, либо стоит второй карты.

Формат данных проверяем и на клиенте (`utils/helpers/target.ts`) — не «на
всякий случай», а вполне конкретно: у одного из поставщиков проверка
аккаунта разрешена раз в десять секунд с адреса, и тратить этот лимит на
опечатки нельзя. Правда при этом остаётся одна — серверная.

## Ключ в поле ввода

Формат кода задаёт бэкенд (`common/codes.py` в k30-api). На витрине —
только то, что нужно полю: подставить дефисы по мере набора, привести
регистр, разложить похожие символы (O→0, I/L→1) и понять, набран ли код
целиком, чтобы не дёргать сервер на каждой букве. Настоящую проверку —
контрольный символ и существование ключа — делает бэкенд: дублировать её
здесь значило бы получить две правды вместо одной.

## Оформление

Тема тёмная и единственная: витрину открывают, чтобы ввести ключ и уйти, а
активируют чаще всего ночью. Фирменный цвет золотой (`#e2a93a`), на заливке
текст тёмный — белый по золоту не проходит по контрасту.

Токены цветов, отступов, радиусов и типографики — в `src/styles/tokens.scss`,
миксины (контейнер, медиазапросы, типографика, кольцо фокуса) — в
`src/styles/mixins.scss`. Размеры заголовков плавают через `clamp` вместе с
шириной экрана, а не прыгают на брейкпоинте.

Вёрстка мобильная в основе: базовые значения — телефонные, широкие экраны
добавляют к ним через `media_up`.

## Анимации

Общие кривые, длительности и варианты — в `src/components/motion/tokens.ts`,
чтобы движение по всему сайту читалось одинаково. Там же примитивы:

- `Reveal` — блок проявляется, когда доезжает до экрана;
- `Stagger` / `StaggerItem` — список, элементы которого появляются по очереди.

`MotionConfig reducedMotion="user"` стоит в `AppProviders`: при системной
настройке «уменьшить движение» framer-motion сам убирает сдвиги, оставляя
проявление.

Блоки с анимацией приезжают в html с `opacity: 0`, поэтому в `layout.tsx`
лежит запасной стиль в `<noscript>` — без работающего JS страница всё равно
показывает содержимое.

## Кабинет

Токены — SimpleJWT со стороны бэкенда. Refresh лежит в `localStorage`,
access живёт в памяти и протухает за полчаса; `AuthHydrator` меняет refresh
на свежий access при загрузке вкладки, а RTK Query повторяет запрос один
раз после 401.

Кроме заказов там есть **история активаций**. Отдельно от заказов,
потому что это разные вопросы: заказ отвечает «что я купил», активация —
«почему оно не заработало». Второй вопрос и приводит человека в
поддержку, а с историей на экране часть таких обращений заканчивается
сама. Незавершённые активации показываются ссылкой обратно на страницу
ожидания: вкладку часто закрывают, не дождавшись, и вернуться к ней
иначе неоткуда.

Раздел не рисуется вовсе, если попыток не было, — пустая «История» в
кабинете у того, кто ничего не активировал, это шум.

## Разработка

```bash
npm run lint                  # eslint + stylelint
npm run typecheck
npm run format                # prettier
npm run build
```

Правила: prettier и eslint — копия конфигов `face` (одинарные кавычки,
80 колонок, сортировка импортов `simple-import-sort`). Stylelint запрещает
`@import` в SCSS — только `@use`/`@forward`.

## Деплой

Витрина — статика: `output: 'export'`, данные она берёт из API прямо в
браузере, поэтому сервера ей не нужно. Пуш в `main` запускает
[.github/workflows/deploy.yml](.github/workflows/deploy.yml) — сборка и
выкатка на GitHub Pages. Правка в админке видна сразу, пересобирать сайт
из-за неё не нужно.

Адрес: <https://eugenepokalyuk.github.io/k30-next/>

Адреса не зашиты в код, а лежат в переменных репозитория (Settings →
Secrets and variables → Actions → Variables): `API_URL`, `APP_URL`,
`BASE_PATH`. Переезд на свой домен — правка этих трёх полей и перезапуск
workflow, без коммита.

Две вещи, о которых стоит помнить при сборке экспорта:

- `trailingSlash: true` — иначе Pages отдаёт 404 на `/activate`: он ищет
  `activate.html`, а экспорт кладёт `activate/index.html`;
- `.nojekyll` в `out/` — без него Pages прогоняет статику через Jekyll,
  а тот выкидывает каталоги на подчёркивании, то есть весь `_next`.

### Пока нет домена

Витрина открывается по https (иначе Pages не умеет), а бэкенд отвечает по
http на IP. Запросы с https-страницы на http-адрес браузер блокирует как
mixed content: сайт выглядит правильно, но список сервисов пуст, ключ не
проверяется и в кабинет не войти. Чинится это только сертификатом на
бэкенде — порядок описан в README k30-api, раздел «Когда появится домен».

Посмотреть витрину в рабочем виде до этого можно локально: `npm run dev`
против бэкенда на `localhost:8000` или против сервера, указав
`NEXT_PUBLIC_API_URL=http://159.194.237.59/api/v1` — на http-странице
запрос к http-адресу проходит.
