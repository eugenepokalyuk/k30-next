# k30-next

Витрина магазина подписок «К30» (k30market.ru): покупатель вводит код
ключа, сайт определяет сервис и доводит дело до выданной подписки.

Next.js 16 (App Router, статический экспорт), React 19, Redux Toolkit с
RTK Query, SCSS Modules, framer-motion. Всё на TypeScript. Бэкенд —
[k30-api](../k30-api); без него витрина поднимется, но список сервисов и
активация работать не будут.

Раскладка папок взята с `divodivnoe`, конфиги eslint, prettier и
stylelint — с `face`.

## Запуск

```bash
npm install
cp .env.example .env.local
npm run dev                   # localhost:3000
```

Бэкенд при этом должен слушать `localhost:8000`.

### Переменные окружения

| Переменная                     | Зачем                                     |
| ------------------------------ | ----------------------------------------- |
| `NEXT_PUBLIC_API_URL`          | Адрес бэкенда. Публичная: запросы уходят из браузера |
| `NEXT_PUBLIC_APP_URL`          | Канонический адрес витрины, для метаданных и шеринга |
| `NEXT_PUBLIC_SUPPORT_TELEGRAM` | Телеграм поддержки на время загрузки — настоящий адрес приезжает из админки |
| `NEXT_PUBLIC_BASE_PATH`        | Подкаталог сайта. Нужен только на Pages без своего домена |

## Страницы

`/` — главная: поле ввода ключа, лента сервисов, «как это работает»,
вопросы. Живёт в `app/home` и реэкспортируется из корня, чтобы секции
лежали рядом со своей страницей, а не в общем `_components`.

`/activate` — активация, четыре шага от кода до подписки. `/login` — вход.
`/account` — профиль, заказы и история активаций.

## Активация

Четыре шага: **Ключ → Аккаунт → Активация → Готово**.

Проверка данных и подтверждение разделены. Между ними покупатель видит,
на какой аккаунт уедет подписка, — перепутанный аккаунт после активации
уже не отменить.

Устройство этой страницы держится на трёх вещах.

Состав формы приходит с бэкенда. Витрина не знает, у какого поставщика
куплен ключ, и знать не должна: один и тот же сервис у разных
поставщиков просит разные данные — где Organization ID, где User ID.
Поле `targets` в ответе `verify-key` описывает, что показать; когда
вариантов несколько, даём выбрать.

Активация асинхронная, у Claude — около двух минут. Экран ожидания
(`ProgressStep`) не украшение: без него запрос просто висел, а
покупатель, не понимая, идёт что-то или нет, жал кнопку повторно.
Показываем позицию в очереди и счётчик; после двух минут
(`ActivationLongWaitSeconds`) честно говорим, что ждать у экрана
необязательно и можно вернуться по той же ссылке. Темп опроса диктует
бэкенд полем `poll_after` — у поставщиков разные лимиты, и знание о них
живёт на той стороне. Хук: `lib/hooks/useActivationPolling.ts`.

Тон ошибки выбирается по полю `blame`, а не по её тексту. «Вы вставили
данные не из того аккаунта» (`customer`), «у поставщика кончились
подписки» (`provider`) и «это на нашей стороне» (`shop`) требуют от
человека разного, а выглядели бы одинаковым красным прямоугольником.
Кнопку «Повторить» показываем только с разрешения бэкенда (`can_retry`):
у части поставщиков карта после неудачи заморожена, и вторая попытка либо
бесполезна, либо стоит второй карты.

Формат данных проверяется и на клиенте (`utils/helpers/target.ts`) — не
на всякий случай, а по делу: у одного из поставщиков проверка аккаунта
разрешена раз в десять секунд с адреса, и тратить этот лимит на опечатки
нельзя. Правда при этом одна, серверная.

### Опрос статуса

`useActivationPolling` просит RTK Query `skipPollingIfUnfocused`: увели
вкладку в фон — опрашивать незачем. Чтобы это работало, в
`store/store.ts` вызывается `setupListeners`. Без него флаг «вкладка на
виду» вычисляется один раз при создании стора и застывает: ссылку на
активацию присылают в мессенджере и открывают в фоновой вкладке, стор
создаётся при `hidden`, и опрос не начинается вообще — экран ожидания
висит, что бы ни отвечал бэкенд.

Останавливается опрос сам, когда активация дошла до окончательного
состояния. Отдельного таймаута тут нет: зависшую активацию бэкенд сам
переведёт в «разбираем вручную», и это приедет очередным ответом.

## Ключ в поле ввода

Формат кода задаёт бэкенд (`common/codes.py` в k30-api). На витрине
только то, что нужно самому полю: подставить дефисы по мере набора,
привести регистр, разложить похожие символы (O→0, I/L→1) и понять, набран
ли код целиком, чтобы не дёргать сервер на каждой букве. Контрольный
символ и существование ключа проверяет бэкенд — иначе получилось бы две
правды вместо одной.

Проверив ключ на главной, результат кладём в стор и уходим на
`/activate?key=…`, второго запроса не нужно. Страница умеет запросить всё
и сама: по прямой ссылке или после F5 стора нет, и это обычный путь, а не
ошибка.

## Вход

Пароля нет: покупатель приходит с Маркета или из телеграма, логина не
придумывал. Способов два — код на почту и подтверждение в боте, — а какие
показать, решает бэкенд полем в `/auth/options`.

Телеграм подключён диплинком, а не штатным Login Widget: виджету нужен
домен, привязанный в BotFather, а витрина живёт на Pages. Жмём «Войти
через телеграм», открывается бот с одноразовым `nonce`, страница
опрашивает `/auth/telegram/status` и с подтверждением уходит в кабинет.

Момент «вошли» ловит сам эндпоинт RTK Query (`onQueryStarted` в
`k30Api.ts`), а не экран входа: токены приезжают один раз, и пропустить
этот ответ нельзя — заявка гасится сразу после выдачи.

## Кабинет

Токены — SimpleJWT. Refresh лежит в `localStorage`, access живёт в памяти
и протухает за полчаса. `AuthHydrator` меняет refresh на свежий access
при загрузке вкладки, RTK Query повторяет запрос один раз после 401.

Кроме заказов там история активаций. Отдельно, потому что вопросы разные:
заказ отвечает «что я купил», активация — «почему оно не заработало».
Второй и приводит человека в поддержку, а с историей на экране часть
таких обращений заканчивается сама. Незавершённые активации показываются
ссылкой обратно на экран ожидания: вкладку часто закрывают, не
дождавшись, и вернуться к ней иначе неоткуда.

Если попыток не было, раздел не рисуется совсем — пустая «История» это
шум.

## Настройки из админки

Ссылки телеграма, круглая кнопка в углу и блок «Купить ключ» приходят с
`/site-settings` (`useSiteSettings`), частые вопросы — с `/faq`
(`useFaqQuery` в `FaqSection`). Менеджер правит их без пересборки
статики. Выключенный флаг означает, что блок не показывается, поэтому до
ответа сервера всё считается выключенным — иначе кнопка мигала бы на
каждой загрузке.

## Оформление

Тема тёмная и единственная: витрину открывают, чтобы ввести ключ и уйти,
а активируют чаще всего ночью. Фирменный цвет золотой (`#e2a93a`), на
заливке текст тёмный — белый по золоту не проходит по контрасту.

Токены цветов, отступов, радиусов и типографики — `src/styles/tokens.scss`;
миксины (контейнер, медиазапросы, типографика, кольцо фокуса) —
`src/styles/mixins.scss`. Размеры заголовков плавают через `clamp` вместе
с шириной экрана, а не прыгают на брейкпоинте. Вёрстка мобильная в
основе: базовые значения телефонные, широкие экраны добавляют к ним через
`media_up`.

Кривые, длительности и варианты движения собраны в
`src/components/motion/tokens.ts`, чтобы анимации по всему сайту читались
одинаково. Там же `Reveal` (блок проявляется, доехав до экрана) и
`Stagger` / `StaggerItem` (список появляется по очереди).
`MotionConfig reducedMotion="user"` стоит в `AppProviders`: при системной
настройке «уменьшить движение» framer-motion сам убирает сдвиги.

Блоки с анимацией приезжают в html с `opacity: 0`, поэтому в `layout.tsx`
лежит запасной стиль в `<noscript>` — без JS страница всё равно
показывает содержимое.

## Разработка

```bash
npm run lint                  # eslint + stylelint
npm run typecheck
npm run format
npm run build
```

Одинарные кавычки, 80 колонок, сортировка импортов `simple-import-sort`.
Stylelint запрещает `@import` в SCSS — только `@use` и `@forward`.

Сквозную проверку активации удобно гонять против заглушки поставщика, а
не живой карты: каждый прогон на настоящем поставщике стоит карты.

## Деплой

Витрина — статика (`output: 'export'`), данные берутся из API прямо в
браузере, сервер ей не нужен. Пуш в `main` запускает
[.github/workflows/deploy.yml](.github/workflows/deploy.yml): сборка и
выкатка на GitHub Pages. Правка в админке видна сразу, пересобирать
из-за неё нечего.

Адрес: <https://eugenepokalyuk.github.io/k30-next/>

Адреса не зашиты в код, а лежат в переменных репозитория (Settings →
Secrets and variables → Actions → Variables): `API_URL`, `APP_URL`,
`BASE_PATH`. Переезд на свой домен — правка этих трёх полей и перезапуск
workflow, без коммита.

Про экспорт стоит помнить две вещи. `trailingSlash: true` — иначе Pages
отдаёт 404 на `/activate`: он ищет `activate.html`, а экспорт кладёт
`activate/index.html`. И `.nojekyll` в `out/` — без него Pages прогоняет
статику через Jekyll, а тот выкидывает каталоги на подчёркивании, то есть
весь `_next`.

### Почему API_URL ведёт на sslip.io

На проде `API_URL` — `https://159-194-237-59.sslip.io/api/v1`, хотя
бэкенд живёт на `159.194.237.59`. Адрес странный, но менять его на голый
IP нельзя.

Pages отдаёт витрину только по https, а с https-страницы браузер не
отправляет запросы на http-адрес — блокирует как mixed content, ещё до
отправки. Выглядит это обманчиво: сайт открывается и верстается
правильно, но список сервисов пуст, ключ не проверяется и в кабинет не
войти; в консоли `blocked:mixed-content`. Правками в коде витрины это не
лечится, запрет браузерный.

Значит, бэкенду нужен https, а сертификат на голый IP не выпустить.
[sslip.io](https://sslip.io) резолвит `159-194-237-59.sslip.io` в тот
самый `159.194.237.59`, и на это имя Let's Encrypt выдаёт обычный
сертификат. Решение временное, до `api.k30market.ru`; порядок переезда —
в README k30-api.

Локально ограничения нет: `localhost:3000` открывается по http, поэтому в
`.env.local` годится любой адрес — `http://localhost:8000/api/v1` против
своего Django или `http://159.194.237.59/api/v1` против боевого бэкенда.
Второй удобен, когда витрину правишь на реальных данных.
